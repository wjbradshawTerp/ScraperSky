## 1. The goal

ScraperSky started as a single-account X/Twitter scraper. The target is to grow it into the infrastructure described in the "Agentic Sockpuppet Experiment" research paper (Do Won Kim, design; Will Bradshaw, implementation) — a platform that runs many LLM-driven sockpuppet accounts through a controlled **Observation → Decision → Execution → Logging** loop, under an **Experiment Orchestrator** that manages experimental phases and randomized interventions.

The paper's architecture has five modules:
1. **Configuration Layer** — researcher-facing config defining the experiment (`experiment_design`, `sockpuppet_config`, `intervention`, `data_collection` namespaces).
2. **Sockpuppet Initialization & Persona Construction** — cold-start behavior (follow/engage until stopping criteria met, using a *restricted* action set) + a persistent `persona_prompt` (profile summary + behavioral rules) that governs an agent's decisions for the whole experiment.
3. **Agent Runtime** — the per-activation decision cycle: (1) Observation of platform state, (2) Prompt Construction (persona + platform state + experiment context + behavioral rules), (3) Decision (LLM call → structured `{action, target_object, system_response, execution_status}`), (4) Execution, (5) Logging. Activation timing is sampled from a configurable distribution (e.g. truncated power-law), not a fixed schedule. The *same* five-stage cycle runs during cold-start, pre-treatment, and post-treatment — only the allowed action set and experiment phase differ.
4. **Experiment Orchestrator** — global experiment state: account provisioning, per-agent activation scheduling, treatment assignment/randomization, phase transitions (init/pre-treatment → treatment → post-treatment), failure recovery, reproducibility logging.
5. **Data Collection & Storage** — immutable JSONL records: platform observations (for_you_feed, home_timeline, engagement_log, intervention_history) and full runtime logs (prompt, model output, action, execution result).

**Case study to reproduce**: the "Mercury Project" muting experiment. Sockpuppets are seeded from real Mercury participants' pre-treatment behavior (persona = summarized engagement/following patterns), split into control/treatment arms, and after a pre-treatment observation period, treatment agents mute a random 70% of a list of "untrustworthy" accounts they follow. Both arms continue being observed through a post-treatment period. The goal is to causally measure the effect of muting on subsequent exposure/engagement.

**Standing decisions** (already made with the user, don't re-litigate):
- Build order: **bugfixes → config → observation/action split → multi-account → LLM Agent Runtime → orchestrator** (roughly mirrors the paper's own module dependency order).
- Agent Runtime will use **LangChain** (user's explicit choice over a raw Anthropic-API-only design).
- GUI is **deprioritized** — paper only calls for a config file + a "Monitor & Control" component, not a UI. Revisit only after the orchestrator exists.
- Account provisioning / cookie automation is real ToS/detection risk — sequence it deliberately with its own risk review, and the user should confirm IRB/ethics approval covers automated multi-account behavior before scaling past 1 account. This is a process question for the user, not something to resolve in code.
- Multi-account credential storage was resolved as: **one gitignored `accounts.yaml`** with a list of account entries (credentials + optional per-account overrides), not per-account `.env` files or suffixed env vars. See Phase 3 below.
- Platform action rate limits (from live testing): **follow — 15/15min, 400/day**. Likes/mutes: no rate-limit issues detected so far. These constrain `initialization_params.min_follows` and any future activation-scheduling validation (Phase 4/5) — a configured `min_follows` must be reachable within `max_initialization_days` given the follow rate limit.
- **Retweet has NO established daily cap from our data, despite one error message saying otherwise.** On 2026-09-09 a retweet attempt returned `Authorization: You have reached your daily limit for sending Tweets and messages. (344)` at 19:21:26 — but another retweet **succeeded at 19:24:17**, three minutes later, and only **7 retweets had succeeded all day**. So that message was not a true quota exhaustion, and no cap can be inferred from it. Treat `344` the same as the `226` "looks automated" and the bare `404`s: one of several responses X returns to this account under rapid automated retweeting, not a reliable signal about remaining quota. See the retweet-reliability entry in Phase 4's follow-ups.

### Phase 4 — Agent Runtime (LLM decision loop) ✅ (live-verified; committing now — see repo for the actual commit hash)

Implements the paper's five-stage cycle using **LangChain** (`langchain-ollama` against a local Ollama server — the user's preference over a paid API; swap the model/provider in [src/runtime/decision.py](src/runtime/decision.py)): Observation → Prompt Construction → Decision → Execution → Logging. `TwitterScraper.run_agent_runtime()` ([src/scraper/twitter.py](src/scraper/twitter.py)) runs this loop forever, replacing the old scripted single-target observation loop for any account with `sockpuppet_config.persona_prompt` configured (`Account.agent_runtime_enabled`) — cold-start (4a) still runs first either way.

- **4a. Cold-start initialization mode ✅.** Restricted-action loop (follow/like/repost only, no mute/unmute) that runs before observation begins when `sockpuppet_config.initialization_params` is configured. Loops until `min_follows`/`min_engagements` are met or `max_initialization_days` elapses; progress persists in `agent_state` so a restart resumes rather than restarting, and a completed run never re-triggers. Follows are sampled (shuffled) from the configured `account_lists` and self-throttled to stay under the live 15/15min rate limit ahead of a 429. `main.py`'s `validate_cold_start()` rejects a `min_follows` that isn't reachable within `max_initialization_days` given the 400/day limit, at startup. Still a separate scripted loop, *not* routed through the new decision cycle (see the note near the end of this section).
- **4b. `AgentState` schema expansion** ([src/storage/agent_state.py](src/storage/agent_state.py)) — partial by design. `interaction_history`/`initialization_progress` landed with 4a; `record_interaction()` also accepts `execution_status`/`system_response`; `recent_interactions()` and `has_acted_on()` landed during live testing (see below). `persona_prompt`/`account_metadata`/`internal_memory` remain unbuilt — the persona text lives in a config-referenced file (`Account.get_persona_prompt_text()`) rather than in `agent_state`, and nothing needs per-agent `account_metadata`/`internal_memory` yet. Revisit if/when that changes.
- **4c. `execute_action()` structured return ✅** ([src/scraper/twitter.py](src/scraper/twitter.py)). Returns `{"execution_status": "success"|"failure"|"skipped", "system_response": {...}|None}` instead of a bare `bool` — `favorite_tweet`/`retweet`/`mute_user`/`follow_user` all return a small result dict (`success`/`status_code`/`reason`) that `execute_action()` wraps. `follow_all()` and cold-start check `result["execution_status"]` instead of truthiness.
- **4d. `No Action` ✅.** `execute_action("no_action")` short-circuits before the network with `{"execution_status": "skipped", "system_response": None}`. The `Decision` schema ([src/runtime/schema.py](src/runtime/schema.py)) includes it as a Literal option.
- **4e. Prompt construction ✅ (per-post as of the 2026-08-18 redesign below)** ([src/runtime/prompt.py](src/runtime/prompt.py)) — `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)` assembles `Prompt = Persona Prompt + Platform State + Experiment Context + Behavioral Rules` for ONE observed post at a time (+ a recent-actions section added during live testing, see below) as labeled sections. `experiment_context` (`TwitterScraper._build_experiment_context()`) provides `experiment_id`/`phase`/`treatment_arm`/`intervention_status`/`current_time` — the first three sourced from `experiment_design.experiment_name` + `sockpuppet_config.{phase,treatment_arm}`, explicit stand-ins for what the Experiment Orchestrator (Phase 5) will assign per-agent once it exists. `runtime_constraints` from the paper's schema isn't a separate field; it's folded into the `allowed_actions` list passed as behavioral rules. **Safety validation** (`_validate_decision()`) rejects a decision — downgrading to a logged `no_action` rather than calling `execute_action()` — if: the action isn't in `allowed_actions` for the current phase; the tweet's own data is missing the id `_resolve_target()` needs for that action (a data-quality problem, not a hallucination — see the per-post redesign below, there's no LLM-supplied id left to hallucinate); or the exact `(action, target)` pair already succeeded before (added during live testing, see below).
- **4f. Config schema widening** — landed: `sockpuppet_config.persona_prompt` (file path, resolved like `account_lists`), `sockpuppet_config.phase`/`treatment_arm` (Phase 5 stand-ins), `sockpuppet_config.activation_schedule.{distribution,min_interval,max_interval}` (parsed via new `src/utils/duration.py`; `truncated_powerlaw` approximated as log-uniform sampling, no shape parameter is given in the paper's schema to do better), `data_collection.logging` (`full`/`minimal`), `experiment_design.experiment_name`. Still unbuilt, deliberately: `experiment_design.{treatment_arms,randomization,phase_durations}` and all of `intervention` — nothing in Phase 4 consumes them; they're genuinely the Experiment Orchestrator's (Phase 5) job.
- **Simultaneous multi-target observation ✅** — `TwitterScraper.observe()` fetches one page of every configured target per activation (vs. the old continuous single-target scroll), returning `platform_state = {target_name: [tweet, ...]}`. `main.py`'s target-count validation now only enforces "exactly one" outside Agent Runtime mode.
- **Runtime logging ✅** — a second `FileManager` instance (`stream="runtime_log"`, [src/storage/file_manager.py](src/storage/file_manager.py)) writes one JSONL entry per decision with the paper's `runtime_log` fields (`observation_id`, `timestamp_utc`, `phase`, `selected_action`, `target_object`, `execution_status`, `system_response`, plus `constructed_prompt`/`model_output` unless `logging: minimal`), plus `observed_tweet_id`/`target_name` added for the per-post redesign below (needed since `target_object` alone can't identify which post a `no_action`/mute/follow row was about). Since the per-post redesign, this is one row per post evaluated, not one row per activation — `observation_id` still groups every row from the same activation together. The observed `platform_state` is persisted separately via the existing observation `FileManager`, matching the paper's treatment of platform observations and runtime logs as two distinct data streams.

#### Phase 4 live end-to-end testing (2026-08-18) — 3 real findings, fixed

Full `docker compose up` run with two real accounts in `accounts.yaml`: `primary` (no `sockpuppet_config.persona_prompt` — runs the old scripted single-target loop, unaffected by any of this) and `secondary` (persona = `personas/bradshaw_persona.txt`, a real gitignored persona the user wrote — see the orientation section below). Confirms the core milestone: **the full Observe → Prompt Construction → Decision → Execution → Logging cycle works end-to-end against the live X API** — real `like` actions landed successfully (`200 OK`, confirmed against the real account).

Also confirmed and closed out:
- **Activation-interval sampling is statistically sound.** An early observation (2 samples landing near the top of the configured range) looked suspicious; a longer run produced 6 samples (32s–111s) spread across nearly the full configured `[30s, 120s]` window, confirming `_sample_activation_interval()`'s `random.uniform`/log-uniform sampling works correctly — the earlier concern was just small-sample noise.
- **Activation spacing reminder**: the paper wants realistic **minutes-to-hours** spacing (`min_interval: 15m, max_interval: 6h` in its own worked example) to approximate real usage. The short `30s`–`2m` values used for testing are explicitly test-only — widen `secondary`'s `activation_schedule` before treating a run as a real experiment session.
- **`recent_interactions` fix landed**: `AgentState.recent_interactions(limit, exclude_actions)` + a new `=== YOUR RECENT ACTIONS (avoid repeating these) ===` prompt section so the model can see what it already did. **Necessary but not sufficient on its own** — see finding 1 below.

**Three findings from direct inspection of a real `runtime_log.jsonl`** (not fixture tests — this is what live testing surfaced that no amount of mocking would have caught):

1. **Repeats persisted even after the `recent_interactions` fix.** Checked the actual constructed prompt for a repeat decision: it correctly listed the target as already-liked, and the model liked it again anyway. A soft "please don't repeat yourself" instruction is not reliably honored by a 7B local model under simultaneous structured-output constraints. **Fixed with a hard rule, not a better hint**: `AgentState.has_acted_on(action, target)` + a third rejection branch in `_validate_decision()` — an exact repeat of a previously *successful* `(action, target)` pair is now always downgraded to `no_action`. A different action on the same target, or the same action on a new target, is still allowed.
2. **`follow` never triggered — a real bug, not a model failure.** The test persona's follow condition was "*fighting-game account with 1000+ followers*." `_format_tweet()` never rendered follower count at all, even though `build_tweet_object()` already collects `author.followers` — the model had no way to ever evaluate that condition. **Fixed**: `author_followers` added to the rendered tweet line in `_format_tweet()`.
3. **`mute` never triggered despite genuine matching content appearing.** Scanned all 15 real observed feeds in the log for political/Trump content (the persona's explicit "almost always mute" trigger) — cycle 1 really did contain a Trump-related tweet, and the model liked an unrelated tweet instead of muting it. This is a **genuine reasoning limitation** of a 7B model checking multiple persona rules against many candidates in one pass, not a data/code bug like #2. **Mitigated, not guaranteed-fixed**: added a rules line telling the model to explicitly check every specific "always"/"almost always" trigger condition before defaulting to its most common action. Whoever picks this up should re-test and see how much this actually moves the needle — it may need a stronger intervention (e.g. a two-pass decision, or scoping the platform_state down per cycle) if it doesn't.

All three fixes verified via fixture tests (mocked, no live calls — `has_acted_on` behavior, `_format_tweet` follower rendering, `_validate_decision`'s new rejection branch). **Not yet re-verified live** at the time these three findings were written — re-running `secondary` and checking whether repeats/follow/mute now behave correctly was the natural immediate next step, and turned out to surface a deeper root cause (below).

#### Follow-up (2026-08-18, same day): root cause of finding 3, and why follow rarely fired either

A user-reported log (all 15 decisions in `run_20260818-103350_runtime_log.jsonl` were `like`, never mute/follow/retweet) prompted a direct, reproducible diagnosis: isolated `DecisionEngine.decide()` calls (real Ollama, `qwen2.5:7b`, no live X API) against small engineered feeds, run 10-12x each to see the actual decision distribution rather than judging from one-off samples.

- **Confirmed not a code/validation bug**: the saved `model_output` field in the real runtime logs shows the LLM itself emitting `action: "like"` in all 29 decisions logged that day (the `no_action` entries visible in `selected_action` are `_validate_decision` correctly downgrading repeat-`like`s via `has_acted_on` — the raw model output was still always `like`).
- **Root cause 1 — competing salience crowds out conditional triggers.** A feed with only a mute-worthy tweet (no fighting-game content) *did* get muted ~30% of the time. The same mute-worthy tweet placed alongside a fighting-game tweet got muted 0/10 times — the model reliably defaults to its "primary" persona behavior (like/retweet) whenever anything resembling it is present, rather than checking conditional rules first. This matches the finding-3 hypothesis above (7B model, multiple rules, one pass) but is worse than it looked: it's not "sometimes misses it," it's "never checks it once a like-candidate exists in the same context."
- **Root cause 2 — id-type confusion for follow/mute, once the model does try to act on the author.** Even after root cause 1 was fixed (below) and mute/follow decisions started coming through, the model would sometimes hand back the tweet's `tweet_id` as `target_object` for a `mute`/`follow` action instead of the author's `user_id` — because `_format_tweet()`'s old `[id: ..., author_id: ..., ...]` labeling made "id" ambiguous about which value maps to which field. `_validate_decision()`'s hallucinated-id check would then correctly reject it (the tweet_id genuinely isn't a valid user_id) and silently downgrade a well-reasoned mute/follow to `no_action` — so this bug would have kept suppressing mute/follow even after root cause 1 was addressed.
- **Fix, verified empirically (not just fixture tests) against real Ollama output**:
  - [src/runtime/schema.py](src/runtime/schema.py): `Decision` gained a `trigger_check: str` field placed *before* `action` — pydantic/tool-calling field order is generation order for structured output, so forcing the model to articulate which persona trigger (if any) matches which observed item, before it commits to `action`, changed behavior directly (this is a generation-order effect, not just better wording).
  - [src/runtime/prompt.py](src/runtime/prompt.py): `_format_tweet()` relabeled `id:`/`author_id:` to unambiguous `tweet_id:`/`author_user_id:`; `RUNTIME_BEHAVIORAL_RULES` updated to match and to spell out that follow/mute target the author's `author_user_id`, never the `tweet_id`.
  - Same engineered scenario, 12 trials each, real model: mute went from **0/10 → 9/12** (correct `author_user_id` target every time it fired); follow went from **never observed in any live log that day → 1/12** (correctly targeted) in a scenario with no competing mute trigger — a real fix, though follow's low rate looks consistent with the persona's own weaker "quite likely" language rather than a remaining bug. Retweet also came through reliably once mute/follow stopped being invisible to the model.
- **Not fully solved**: the persona's literal probability language ("like 75% of the time and repost 25% of the time") still isn't something a language model reliably implements as a calibrated sampling rate per decision — that's a more fundamental limitation than this fix addresses, worth knowing about if the eventual analysis assumes literal frequency compliance.
- **Live re-verification of the actual `secondary` account with these two changes is still the next step** — the above was validated via direct `DecisionEngine` calls against engineered feeds, not a full `run_agent_runtime()` cycle against the live X API.

#### Fourth follow-up, same day: per-post redesign — one LLM call per post, not one per batch

**Checked against the paper first** (`SockPuppet (1).docx`, extracted from the user's Downloads folder via the docx skill, since it wasn't otherwise available in this conversation). **Implementation** (planned via `EnterPlanMode`, one Plan-agent review pass, then executed):
- [src/runtime/schema.py](src/runtime/schema.py): `Decision` drops `target_object` entirely. This *fully* closes the tweet_id-vs-author_user_id confusion bug from the second follow-up above (previously only mitigated via clearer labeling, never eliminated). Kept `trigger_check` (still forces the model to reason before committing to `action`, field order still load-bearing), reworded for a single-post framing.
- [src/runtime/prompt.py](src/runtime/prompt.py): `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)` replaces the old whole-`platform_state` version. `format_platform_state()` removed (dead code once nothing calls it); `_format_tweet()` reused as-is for the single "OBSERVED POST" section. `RUNTIME_BEHAVIORAL_RULES` rewritten: dropped all now-meaningless `target_object`-format rules; reframed "prefer a different item from the feed" (assumed other items to fall back to) into "choose a different action on this post, or no_action"; reframed "scan the feed for a matching trigger" into "check THIS post specifically."
- [src/scraper/twitter.py](src/scraper/twitter.py): new `_resolve_target(action, tweet)` derives the target deterministically (tweet_id for like/retweet, author's user_id for follow/mute, None for no_action) — can still legitimately return `None` if the tweet's own data is missing that id (a data-quality issue, not hallucination, gets a distinct log message). `_validate_decision(decision, tweet, allowed_actions)` (was `(decision, platform_state, allowed_actions)`) drops the hallucinated-id check entirely (structurally impossible now) and calls `_resolve_target()` instead. `_log_runtime_cycle()` gains `observed_tweet_id`/`target_name` params (see Runtime logging note above). `run_agent_runtime()`'s outer loop is unchanged (still one `observe()` snapshot per activation, still samples the next interval only after all posts from this activation are processed) but the single decide/validate/execute/log block is now a nested `for target_name, tweets in platform_state.items(): for tweet in tweets:` loop, with `experiment_context`/`recent_interactions` recomputed on every inner iteration (so `current_time` doesn't go stale across a long inner loop, and an action taken on post #3 is visible to post #10's prompt in the same activation). #### Fifth follow-up, same day: distinguishing WHY a row is `no_action`

#### Eighth follow-up (2026-08-26): retweet's silent no-op — a real bug, not a repeat of the id-confusion history above

Live testing (persona changed to prefer `retweet` for one run, specifically to exercise this path) surfaced a new failure mode: `execute_action("retweet", ...)` returned `"execution_status": "success"`, `"system_response": {"status_code": 200, "reason": "OK"}`, but the repost never appeared on the post or the account's Reposts tab.

**Root cause**: `favorite_tweet()`/`retweet()` ([src/scraper/twitter.py](src/scraper/twitter.py)) determined success from `r.status_code == 200` alone and discarded the response body entirely (`system_response` only ever stored `status_code`/`reason`). X's GraphQL mutations routinely return **HTTP 200 with an `errors` array and null data** when the mutation itself fails — a 200 status is not proof the action happened, and the discarded body meant there was no way to see *why* from the logs.

**Fix**: both methods now route through a shared `_post_graphql_mutation()` helper that parses the JSON body and treats a non-empty `errors` array as failure, surfacing the real error message as `reason`. Also added `"dark_request": False` to `CreateRetweet`'s variables (part of X's real mutation payload for this endpoint, plausibly why it silently failed while `FavoriteTweet`, which doesn't need it, worked).

**Re-run with the fix in place surfaced the actual reasons**, confirming this wasn't a code bug but genuine anti-automation behavior from X:
```
retweet → 404 Not Found                                                              (x4)
retweet → 200 OK, but "Authorization: This request looks like it might be automated" (x2)
like    → 200 OK, but "Authorization: Actor (uid: ...)..."                            (x1, recovered afterward)
```
The mix of 404s and an explicit "looks like it might be automated" message on the *same* endpoint (rather than a uniform failure mode, which a stale query hash would produce) points to X's backend giving inconsistent/obscured responses to a request it's flagged as automated — retweet appears to be far more heavily monitored than like/follow/mute. `like`/`follow`/`mute` kept succeeding throughout the same run, so this is a per-action/per-moment detection heuristic, not an account-wide lockout. **A re-run the same day came back clean** (no automation rejections), consistent with this being an intermittent, behavior-triggered detection rather than a permanent block. Treat as a documented platform-behavior finding, not something to engineer around.

**Also fixed the same day**: `execute_action()` now logs a clear `[action] {action} on {target} FAILED: {reason} (status_code=...)` line whenever *any* action fails (like/retweet/follow/mute), for every caller that goes through it (the runtime decision loop, cold-start follows/engagements, `follow_all()`) — previously a failure's reason was only ever visible by digging into `runtime_log.jsonl`'s `system_response`, easy to miss live.

Both fixes syntax-checked; the GraphQL-error-body fix was live-verified via the re-run above (real error messages surfaced correctly). **Known residual gap, not new**: if a mutation returns `200` with an unparseable JSON body, `errors` stays `None` and it's still reported as success — same laxness the old status-only check had for that specific edge case, not fully closed by this fix.

### Empty-batch exponential backoff (2026-08-18)

The `primary` account (old scripted `for_you_feed` loop, no persona) was reported to be collecting fewer new posts over time — matches the pre-existing "For You tab pagination is not indefinite" known issue above: `_scrape_timeline()` was hammering the API with only the flat `scroll_delay` between fetches even when an entire page came back as 100% already-seen duplicates.

Added exponential backoff scoped to exactly that condition: in `_scrape_timeline()` ([src/scraper/twitter.py](src/scraper/twitter.py)), a run of consecutive batches with zero new tweets (after the existing `seenTweetIds` dedup) now waits `empty_batch_backoff_base × 2^n` seconds, capped at `empty_batch_backoff_max`, on top of `scroll_delay` — reset to zero the moment a batch has any new tweet. Only applies to `for_you_feed`/`search` (the two `track_seen_ids=True` targets, where "new vs. duplicate" is actually computed); `home_timeline` doesn't dedupe at all today and wasn't touched. Three new config keys (`empty_batch_backoff_base` default `5`, `empty_batch_backoff_max` default `300`, `empty_batch_backoff_jitter` default `0.2`), per-account overridable like the rest — added to `config.yaml`, `accounts.yaml.example`'s exhaustive reference block, and README's config table. **Live-verified (2026-08-26)**: `primary`'s empty-batch stretches now visibly back off instead of hammering at a flat 2s.

**Follow-up, same day**: per the user's request, the backoff is now jittered rather than a clean exact doubling -- each wait is `(base × 2^n)` randomized by `± empty_batch_backoff_jitter` (default ±20%, still capped at `empty_batch_backoff_max`), so consecutive waits don't form a mechanically perfect 1x/2x/4x/8x/... sequence, which would itself be a detectable non-human pattern. Verified the formula's distribution in isolation (samples cluster around the doubled value with the expected spread at several `n`); **live-verified (2026-08-26)** alongside the base backoff confirmation above.

Also completed this session, smaller items: `accounts.yaml.example` now has an exhaustive `reference_example` block documenting every possible per-account field (standing instruction from the user — keep this in sync whenever a new config field is added, don't treat it as a separate follow-up); `.gitignore` now excludes everything under `personas/` except `example_persona.txt.example`, so the user's real persona file(s) never get committed.

### Phase 5 — Experiment Orchestrator ✅ (not yet committed, not yet live-verified)

Implements the paper's seven Experiment Orchestrator responsibilities as a **shared coordinator**, not a central scheduler: every account keeps running its own already-verified `run_cold_start()`/`run_agent_runtime()` loop, in its own thread, completely unchanged in control flow. A new thread-safe `ExperimentOrchestrator` object (constructed once in `main.py`) is shared across every opted-in account's thread; each loop consults it instead of static per-account config for phase, treatment arm, the follow-rate budget, and reproducibility logging. This was a deliberate choice over a literal central single-loop scheduler (closer to the paper's own wording, but a much bigger rewrite of Phase 4's live-verified loop internals for little practical benefit at this scale) — confirmed with the user before implementation.

**Opt-in, zero behavior change for anything not part of a formal experiment**: setting `experiment_design.treatment_arms` (a non-empty list) on an account is what opts it in (`Account.treatment_arms` property, [src/config.py](src/config.py)). `main.py` computes this gate once per account (`orchestrator if account.treatment_arms else None`) and passes it into `run_account()`/the scraper constructor — an account with no `treatment_arms` gets `orchestrator=None` on its `TwitterScraper` even when a global orchestrator exists for sibling accounts in the same process, so no code path in `twitter.py` can reach it. Confirmed against the user's real `accounts.yaml` (`primary`/`secondary`, neither opted in): both parse and validate identically to before this phase.

New package [src/orchestrator/](src/orchestrator/) (mirrors `src/runtime/`'s schema/prompt/decision split):
- **`state.py`** — `ExperimentState`: persisted global state (`<OUTPUT_DIR>/state/_experiments/<slug(experiment_name)>/orchestrator_state.json`). Unlike `AgentState` (one instance, one owning thread, no locking needed), this object is touched concurrently by every orchestrated account's thread, so every mutation goes through one `threading.Lock`, and writes are atomic (write-to-`.tmp` then `os.replace()` — a torn write here would corrupt randomization/intervention history that's much harder to reconstruct than a per-account state file).
- **`randomization.py`** — pure, seeded functions: `assign_treatment_arms()` (a single seeded shuffle + slice-by-cumulative-ratio, not a per-account hash draw, so a small roster still hits the configured ratio *exactly*) and `seeded_rng()` (a namespaced `random.Random` so treatment assignment and intervention target sampling don't share a draw sequence).
- **`log.py`** — `ReproducibilityLog`: reuses `FileManager`'s exact JSONL/append-only/envelope convention (no new logging abstraction) via `platform="_orchestrator"`, sentinel `account_name="_experiment"` — the first non-account-namespaced log/state path in this codebase, deliberately using the same leading-underscore convention in both places so it's clearly not a real account.
- **`orchestrator.py`** — `ExperimentOrchestrator`: composes the three above, owns the phase-transition tick thread, exposes the only API `twitter.py`/`main.py` touch.

**Treatment assignment**: computed once for the whole participating-account roster and reused verbatim (not re-derived) on every restart once persisted, so a later `randomization.seed` change in config can never silently reassign an already-committed experiment (the orchestrator reads back `ExperimentState`'s *persisted* seed, not the live config value, for every subsequent randomness draw). **Originally done eagerly at orchestrator construction; corrected 2026-09-09 to fire at the END of pre-treatment** (`_ensure_treatment_assignments()`, called from the pre_treatment→treatment transition) per the paper's section 3.3/3.4 — "At the conclusion of the pre-treatment period, the Experiment Orchestrator assigns each sockpuppet to an experimental condition." That ordering matters beyond fidelity: `treatment_arm` is genuinely `None` (and reported as such in every prompt's `experiment_context`) throughout pre-treatment, so the baseline period is condition-blind by construction rather than by the persona happening not to read the field. Construction still assigns as a fallback when resuming an experiment already past pre-treatment.

**Phase state machine**: `PHASE_SEQUENCE = ["pre_treatment", "treatment", "post_treatment"]` in `orchestrator.py` — collapses the paper's "init/pre-treatment" into one starting phase, since cold-start's own `"initialization"` phase string (per-account, `agent_state`-driven) already covers "init" and is unrelated to this machine despite the shared vocabulary. `_allowed_actions_for_phase()` in `twitter.py` needed **no code change**: it already routes any non-`"initialization"` phase (including the new `"treatment"`) to the full action set, which is correct — `mute` must stay agent-selectable via persona/LLM decision in every phase, since the bulk intervention mute is a distinct, orchestrator-triggered action, not a replacement for organic persona-driven muting in either arm. `experiment_design.phase_durations` (new config, shorthand durations via the existing `parse_duration()`) drives automatic transitions, checked by a dedicated tick thread (`ExperimentOrchestrator.start()`, default 60s poll, overridable via constructor for fast tests) — a phase with no configured duration never auto-transitions.

**Cross-account follow-rate coordination**: closes a gap this roadmap already flagged ("must also respect the 15/15min follow rate limit across concurrently-active agents") — previously `_throttled_follow`'s per-account `self._follow_timestamps` meant N concurrently-running accounts could each believe they had their own fresh 15/15min budget. The shared check (`ExperimentOrchestrator.acquire_follow_slot()`, same sliding-window algorithm, same constants, just shared across threads via its own lock) is folded directly into `execute_action()` for orchestrated accounts, not just `_throttled_follow()`'s callers — this closes the gap for cold-start follows *and* agent-runtime-driven follow decisions (which had zero proactive throttling even before this phase) in one change. `_throttled_follow()` now delegates straight to `execute_action()` when orchestrated, avoiding double-throttling against a budget the account no longer owns alone. Not persisted to disk — a restart resetting the shared window is a safe, conservative outcome, not a correctness issue.

**Intervention execution**: new top-level `intervention` config namespace (sibling to `experiment_design`/`sockpuppet_config`/`data_collection`, matching the paper's own Configuration Layer module list), read per-account. `TwitterScraper.run()` registers itself with the orchestrator (`register_scraper()`) right after `follow_all()`/before `run_cold_start()`, giving the orchestrator a live scraper to execute through — reusing `execute_action()` exclusively, no parallel action-execution path. Guarded against ever running twice by an atomic `"pending"→"running"→"completed"` claim in `ExperimentState`, checked from three places (a phase transition, late scraper registration, and a cheap defensive check once per `run_agent_runtime()` activation) so no ordering race between them can double-fire it. **Refinement found during implementation, not in the original design**: each intervention `execute_action()` call is followed by `agent_state.record_interaction(..., phase="intervention", ...)` — `execute_action()` itself only updates `following_list`/`muted_accounts` bookkeeping on success, not `interaction_history` (that's only ever populated by the run loops themselves), so without this an intervention-muted account wouldn't show up in that account's own `has_acted_on()` check or interaction history, risking a redundant persona-driven mute attempt later and an incomplete research record.

**Failure recovery**: initially visibility only — `main.py`'s `run_account()` calls `orchestrator.log_failure(account.name, repr(e))` before re-raising (and `log_failure` never itself raises, so a broken logger can't mask the real exception). **Extended 2026-09-09 into real recovery** (`record_activation_failure`/`record_activation_success`, `experiment_design.recovery_policy`) — see the paper-completion section below.

**Config schema**: `experiment_design.treatment_arms`/`randomization`/`phase_durations`, and the new `intervention` namespace, documented commented-out-by-default in `config.yaml` and in `accounts.yaml.example`'s exhaustive `reference_example` block (kept in sync per the standing instruction). - **Persona-driven cold-start** (the biggest fidelity gap): engagement selection was `random.choice(["like", "retweet"])` — a coin flip that ignored the persona entirely, while the paper says initialization "executes the same runtime decision cycle used during later experimental phases" with actions restricted. Falls back to the old coin flip only when no persona is configured. This matters because initialization is what shapes the baseline feed the whole experiment then measures.
- **`experiment_context.runtime_constraints`** — the last field in the paper's section 3.3 listing, rendered as a flat string (the whole context dict is dumped `key: value` into the prompt, so a nested dict would reach the model as a Python repr).
- **Poisson activation scheduling** — the paper lists Poisson processes among the supported policies; implemented as exponential inter-arrival draws with the configured window's midpoint as the mean, clamped into the window (the schema gives a window, not a rate — same order of approximation as `truncated_powerlaw`'s log-uniform stand-in). Verified across 500 draws per distribution that every sample lands in `[min_interval, max_interval]`.
- **Multi-target scripted path** — the old non-Agent-Runtime loop now round-robins a bounded number of pages per target (`SCRIPTED_ROUND_ROBIN_PAGES`), so a persona-less account can still collect *both* of the paper's feeds. A single target keeps the original indefinite-scroll behavior byte-for-byte. Dedup caches became per-target so rotations don't reset them or let one feed's ids suppress another's. `main.py`'s "exactly one target outside Agent Runtime mode" restriction is gone.

**Orchestrator.**
- **Termination** — reaching the end of the last phase completes the experiment (`experiment_status: "completed"`), logs a `termination` event, and `should_stop()` goes True. Every long-running loop in the scraper (`run_agent_runtime`, `_scrape_timeline`, `_run_scripted_observation`, cold-start) checks it and returns, so account threads exit, `main()`'s joins return, and the process shuts down cleanly with a summary line. Long sleeps are broken into slices (`_sleep_interruptible`) so a completed experiment is noticed promptly rather than after a multi-hour activation interval.
- **`experiment_status: paused`** — the third status in the paper's listing. Freezes phase transitions and idles every agent (`_idle_while_paused()`) without ending the experiment; a completed experiment can't be un-completed by pausing. There's no control surface to trigger it yet beyond `pause()`/`resume()` on the orchestrator (or editing the state file) — the mechanism exists, a CLI for it doesn't.
- **Real failure recovery** — the paper's responsibility #6 is that the orchestrator "records the failure and reschedules subsequent activations according to the configured recovery policy." Each activation is now wrapped: on failure the agent reports to `record_activation_failure()`, which logs it centrally and returns a backoff (doubling per consecutive failure, capped at `max_backoff`) or `None` to give up after `max_consecutive_failures`. `record_activation_success()` clears the streak so it measures *consecutive* failures. Isolated per agent — one account backing off never touches another's schedule — and a non-orchestrated account keeps the old propagate-and-die behavior.

#### Per-action rate budgets (2026-09-09) — pacing retweets off live data

Retweet succeeded only ~35% of the time in the runs above, so a repost-heavy persona had most of its intended engagement silently fail. Added `sockpuppet_config.action_rate_limits` — per-account, per-action pacing on top of whatever the platform enforces:

```yaml
action_rate_limits:
  retweet:
    max_per_hour: 4
    min_interval: 8m
```

**Both constraints exist on purpose.** In the 2026-09-09 data the clearest refusal correlate was *burst density* (the one unambiguous refusal followed 5 attempts inside 5 minutes; successes #4→#5→#6 were 13s and 29s apart) rather than hourly volume — which an hourly cap alone would happily permit. So `ActionRateBudget` ([src/utils/rate_budget.py](src/utils/rate_budget.py)) enforces a rolling-hour cap *and* a minimum gap.

**Where the numbers come from** — live observation, NOT a documented platform limit: 20 attempts over 68 minutes gave 17.7 attempts/hour, 6.2 successes/hour, 35% success, and a 38-minute clean stretch at 10/hour with no refusal. 4/hour with an 8m floor sits conservatively inside that. Caveats worth keeping in mind: n=20 on one account on one day; the platform's refusal messages proved unreliable (a `344` "daily limit" was demonstrably false), so they can't be used to calibrate; and rate may not even be the causal variable, since 11 of 20 failures were bare `404`s that succeeded on a 5-second retry.

**Non-blocking by design.** Unlike `acquire_follow_slot`, which sleeps until a slot frees (fine for cold-start's follow loop, which has nothing else to do), a capped action inside the per-post decision loop is downgraded to a logged `no_action` with a new `no_action_reason: "rate_capped"` — blocking there would stall a whole activation for minutes per retweet. The agent keeps evaluating the rest of the feed, and the log records exactly why the action didn't happen.

Implementation notes:
- The pacing gate is checked **last** in `_validate_decision`, so a decision that would be rejected anyway (disallowed action, missing id, already-done) doesn't burn a slot.
- Consumed **per decision**, not per attempt — so a retried attempt doesn't take a second slot, making the worst-case attempt rate 2x the configured cap (≤8/hour at the current settings, still well under the 17.7/hour that produced refusals).
- Budgets live on the orchestrator (keyed per account+action, so they show up in the reproducibility log as `<action>_rate_budget` / `capped` scheduling decisions), with an equivalent per-instance fallback for a non-orchestrated account — pacing shouldn't depend on being part of a formal experiment.
- Per-account, not shared across accounts: these pace against per-account platform limits, unlike the follow budget, which is shared precisely because its limit appears to apply across concurrently-active agents.
- `main.py`'s `validate_action_rate_limits()` rejects an unknown action name or a malformed entry at startup.

Verified via fixtures: hourly cap refuses the 5th of 6; `min_interval` refuses a burst the hourly cap would allow; config parsing and malformed-entry rejection; budgets are per-account and per-action (another account/action is unaffected); a capped decision becomes `rate_capped` for both orchestrated and non-orchestrated accounts; and a `repeat`-rejected decision does not consume a slot. Applied to `secondary` in the live config (`retweet: 4/hour, 8m floor`).

#### Pacing verified live + like/retweet dedup (2026-09-09, third run)

Verified via fixtures with an **empty** `interaction_history` — the exact reset scenario that let the live re-like through — plus persistence across a reload, non-cross-contamination between the two lists, failed actions not being recorded, and all four actions still passing on genuinely new targets.

Two follow-ons this implied:
- **The reset procedure now preserves `liked_tweets`/`retweeted_tweets`** alongside `following_list`/`muted_accounts`. Wiping them is precisely what recreated the bug, since it left `interaction_history` as the only record and the reset clears that too.
- **Backfilled the new lists from history** so the guard didn't have to relearn each already-liked tweet by failing on it once: reconstructed from every runtime log, engagement log, and pre-reset `agent_state` backup. `secondary` went 0 → **335 liked / 10 retweeted**; `primary` stayed 0/0 as expected (no Agent Runtime, only intervention mutes). Confirmed the specific tweet that failed live (`2097746866935050536`) is now recognized. Caveat: retweet "successes" recorded before the 2026-08-26 GraphQL error-body fix may be false positives, which is the conservative direction — it skips a retweet that never landed rather than causing a duplicate.

#### Committed, and the arms made comparable (2026-09-14)

**Phases 5 and 6 committed as `80893a4`** — two full phases plus three rounds of live-run fixes had been sitting uncommitted since `8e85f90`. The roadmap's own gate for committing Phase 5 ("not yet live-verified") had been satisfied by the three 2026-09-09 runs.

`untrustworthy_sources.json` was excluded and gitignored rather than committed. It holds ids of real X accounts under the label "untrustworthy", and publishing that list in the repo makes a public claim about named people that the research design never required be public. `untrustworthy_sources.json.example` documents the shape. Note the deliberate asymmetry with `follow_user_ids.json`, which stays committed: a follow list asserts nothing about the accounts in it.

**Two config changes, both aimed at getting usable data out of the next run:**

1. **`primary` now runs the Agent Runtime**, with the same `persona_prompt`, `activation_schedule`, and `action_rate_limits` as `secondary`. This closes issue 5 from the first live run structurally: `primary` was a passive scraper in the treatment arm, unable to engage differently pre- vs post-treatment, so the arms were never comparable in the way the paper requires. Verified that both accounts now resolve to `agent_runtime_enabled: True` with byte-identical persona text, schedule, rate limits, targets, and `experiment_design`.

   **Both accounts deliberately share one persona file.** With no Mercury data, a second persona would have to be invented, which would introduce a persona difference between arms — exactly the confound the intervention is supposed to be the only source of. One shared persona removes it entirely. A real run replaces this with a distinct per-participant synthesized persona, at which point this note should be revisited rather than left as precedent.

2. **Phase thresholds raised from `30m`/3 actions to `2h`/50**, on both accounts (they must agree — `validate_experiment_orchestration` enforces it). `max_action_count` is still the expected terminator; `max_duration` is the safety valve so a quiet feed can't stall a phase.

**What to watch on the next run**, since this is a bigger change than it looks:
- **Runtime is now roughly 10-20x longer.** With two agents each making a per-post LLM call and 50 actions per phase to reach, expect hours, not the 15 minutes the last three runs took. The `2h` per-phase ceiling caps the whole experiment at ~6 hours even if the feeds go quiet.
- **Two agents now share one Ollama instance.** Previously only `secondary` made LLM calls. Two accounts making per-post calls against one `qwen2.5:14b` will serialize, not parallelize — this is the first real test of the capacity concern already flagged under "Remaining roadmap", at the smallest possible scale.
- **`primary` will now take real actions** (like/follow/mute/retweet driven by the persona), where before it only ever observed and ran the intervention mutes. Its retweets are paced by the same 4/hour + 8m floor as `secondary`.
- `activation_schedule` is still the test-only `30s`-`2m` on both. Widening the phases without widening this means more actions at an unrealistically fast cadence — fine for a machinery test, not for a run whose behavioral data is meant to be realistic.

Verified through the real `config.py`/`main.py` startup path: every validator passes for both accounts, including the cross-account consistency check on the new thresholds (parsed as `max_duration: 7200.0, max_action_count: 50`), and treatment assignments are still empty at construction (assignment correctly deferred to end-of-pre-treatment). The only validator that fails is `validate_agent_runtime`'s Ollama reachability check, which fails identically for `secondary` — an artifact of running the validator on the host while `OLLAMA_BASE_URL` points at `host.docker.internal` for the container, not a config problem. **No live run yet with either change.**

## 3. Remaining roadmap

Every module the paper specifies is now implemented (Phases 0-6). What's left before a **real** experiment run is mostly not code:

**Blocked on data/process, not implementation:**
- **Real Mercury personas.** Every persona today is either the committed template or the user's hand-written `bradshaw_persona.txt`. The paper requires each sockpuppet's persona be *synthesized from a real Mercury participant's* pre-treatment engagement + following-dyad data (section 4). That dataset isn't in this repo, and no code exists to turn participant records into a persona prompt — a data-engineering task that needs the dataset first.
- **Real account lists.** The paper's case study needs two: untrustworthy sources *and* prominent news organizations, with per-participant dyad relationships determining which untrustworthy accounts each sockpuppet actually follows. Only a small hand-supplied `untrustworthy_sources.json` exists (4 test ids). `prominent_news_sources` was deliberately not scaffolded — the user opted to configure it when real data is ready.
- **Real sockpuppet population + IRB.** Two test accounts exist; a real run needs a population per arm. Account provisioning is manual, carries genuine ToS/detection risk, and the standing decision is that the user confirms IRB/ethics coverage before scaling past one account per arm.

**Worth deciding before a real run (operational, not code):**
- **Ollama capacity.** Two accounts share one local Ollama server informally. A real population all making per-post LLM calls concurrently against one `qwen2.5:14b` instance will serialize rather than parallelize — worth sizing (or moving to a served/batched setup) before committing to an account count.
- **Comparable arms — partially addressed 2026-09-14.** `primary` had no persona, so it couldn't "engage differently" pre- vs post-treatment — a passive scraper that happened to be in the treatment arm. The paper requires *identical* runtimes across arms ("all agents execute an identical runtime regardless of experimental condition; only the intervention differs"). **Quantified by the 2026-09-09 live run**: 347 observation rows / 5,552 tweets for the treatment arm vs 3 rows / 271 tweets for control — see issue 5 in that run's entry above. `primary` now has the same persona/schedule/rate-limits as `secondary`, so both run the Agent Runtime and the arms are structurally comparable. **Still open**: both accounts share ONE persona file. That's the right call while it removes persona as a confound, but the paper wants each sockpuppet's persona synthesized from a distinct participant — so this is a stand-in, not the end state.
- **Real phase thresholds — raised 2026-09-14, still not research-scale.** The old `30m` / `max_action_count: 3` values produced only 5 real post-treatment actions in the 2026-09-09 run and ended the whole experiment in 7-15 minutes. Now `2h` / `max_action_count: 50` per phase, which should give ~150 real actions across the experiment instead of ~9. Post-treatment is where the effect is measured, so a genuine run still wants the paper's own scale (7d per phase) — and widening the phases without also widening `activation_schedule` (still `30s`-`2m`, explicitly test-only) would just make the agents act unrealistically fast for longer. Those two need to move together.

**Genuinely optional / lower priority (not blocking anything):** a control surface for `pause`/`resume` (the mechanism exists, no CLI does), multiple interventions per experiment (the paper's `intervention_schedule` reads as more general than the single one-shot intervention built), structured logging (replace bare `print()`/`self._log()`), a committed test suite (all verification so far is ephemeral fixture scripts), run-archival (zip old runs), a status CLI (in place of the deprioritized GUI).

## 4. Orientation — key files

- `config.yaml` — default behavioral config shared by every account unless overridden. Non-secret, git-shareable. Read this first to understand default runtime behavior.
- `accounts.yaml` — gitignored, per-account credentials + optional per-account overrides of anything in `config.yaml`. `accounts.yaml.example` is the committed template.
- `src/config.py` — `Account` class (resolved per-account credentials + merged config, including `treatment_arms`/`intervention` since Phase 5); `Settings` singleton (`settings`) loads `config.yaml`/`.env` and exposes `load_accounts()`.
- `src/main.py` — entry point; validates every account's resolved config, constructs at most one `ExperimentOrchestrator` (Phase 5, only if any account has `treatment_arms` set) and starts its tick thread, then runs each account's scraper in its own thread, passing the orchestrator only to accounts that opted in.
- `src/scraper/base.py` — `BaseScraper` ABC, takes an `Account` (`self.account`) and an optional `ExperimentOrchestrator` (`self.orchestrator`, Phase 5, `None` for a non-opted-in account), abstract `run`/`fetch_home`/`fetch_following`.
- `src/orchestrator/` — Phase 5's Experiment Orchestrator package: `state.py` (`ExperimentState`, locked/persisted global state incl. `experiment_status` running/paused/completed), `randomization.py` (seeded treatment-arm assignment + intervention sampling), `spec.py` (translation between the paper's published config vocabulary — `selection_rule: random70`, `execution_time: end_of_pre_treatment`, `randomization.method` — and the orchestrator's internal shape; **start here when adding a config field the paper names**), `log.py` (`ReproducibilityLog`, reuses `FileManager`), `orchestrator.py` (`ExperimentOrchestrator`, the shared coordinator `TwitterScraper` consults when `self.orchestrator is not None`). See the Phase 5 and paper-completion sections above before touching phase/treatment-arm/follow-rate/intervention/termination logic in `twitter.py`.
- `src/scraper/twitter.py` — GraphQL timeline fetchers, `parse_timeline()`, `execute_action()`, all four platform actions, cold-start (`run_cold_start()`), and the Agent Runtime cycle (`observe()`/`run_agent_runtime()`/`_resolve_target()`/`_validate_decision()`/`_log_runtime_cycle()`), all keyed off `self.account`. `run_agent_runtime()` loops per-post within each activation (2026-08-18 redesign) — see Phase 4 below before assuming one decision = one activation. Since Phase 5, `execute_action()`/`_throttled_follow()`/`_build_experiment_context()`/`run_agent_runtime()` all branch on `self.orchestrator is not None` to defer to the shared `ExperimentOrchestrator` instead of static per-account config -- see the Phase 5 section above. **Naming key (2026-08-19), read this before touching timeline-fetching code**: GraphQL operation `HomeTimeline` = X's algorithmic default feed = our `home` target (`fetch_home()`/raw `fetch_home_timeline()`); GraphQL operation `HomeLatestTimeline` = X's reverse-chronological feed = our `following` target (`fetch_following()`/raw `fetch_home_latest_timeline()`). The two are easy to conflate by name alone — see the fuller naming-key comment near the top of this file, and the dated rename entry near the end of Phase 4.
- `src/scraper/x_client.py` — `x-client-transaction-id` generator (X's anti-automation request signing). No per-account state, safe to call from multiple threads.
- `src/runtime/schema.py` — `Decision` pydantic model (the LLM's structured output for ONE observed post: `trigger_check`/`action` only — no `target_object`, since the per-post redesign (2026-08-18) derives that deterministically in `TwitterScraper._resolve_target()` instead of trusting the model to supply it).
- `src/runtime/prompt.py` — `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)`: assembles persona + ONE observed post + experiment context + behavioral rules into the text sent to the LLM (per-post as of the 2026-08-18 redesign — was whole-`platform_state` before that).
- `src/runtime/decision.py` — `DecisionEngine`: wraps a LangChain `ChatOllama` call (local Ollama server, `DEFAULT_MODEL = "qwen2.5:14b"`) with structured output. Swap the model/provider here without touching prompt/schema.
- `src/utils/duration.py` — parses shorthand durations (`"15m"`, `"6h"`, `"7d"`) used by `activation_schedule`.
- `personas/example_persona.txt.example` — template for `sockpuppet_config.persona_prompt` files (profile summary + behavioral tendencies). Not real Mercury data. `personas/bradshaw_persona.txt` (gitignored, real content) is the user's actual test persona — currently wired to the `secondary` account in the user's local (gitignored) `accounts.yaml`, with `sockpuppet_config.activation_schedule` set to short test intervals (30s–2m, not the realistic 15m–6h). `primary` in that same file has no persona configured and still runs the old scripted loop.
- `src/storage/file_manager.py` — JSONL writer, namespaced by account name; timezone is a per-instance param; `stream` param disambiguates multiple concurrent writers per account (observations vs. runtime log).
- `src/storage/agent_state.py` — per-account state persistence: `persona_prompt`/`account_metadata`/`following_list`/`muted_accounts`/`liked_tweets`/`retweeted_tweets`/`interaction_history`/`initialization_progress`/`internal_memory` (the paper's full section 3.2 state). The four platform-state lists are what `_validate_decision`'s already-done guard checks — they outlive `interaction_history`, which a reset wipes, so **anything that resets an account must preserve all four** or the agent starts re-acting on things it already did.
- `README.md` — user-facing setup/config docs, kept in sync with `config.yaml`/`accounts.yaml`'s actual schema each phase.
