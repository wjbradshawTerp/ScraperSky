## 1. The goal

ScraperSky started as a single-account X/Twitter scraper. The target is to grow it into the infrastructure described in the "Agentic Sockpuppet Experiment" research paper (Do Won Kim, design; Will Bradshaw, implementation) — a platform that runs many LLM-driven sockpuppet accounts through a controlled **Observation → Decision → Execution → Logging** loop, under an **Experiment Orchestrator** that manages experimental phases and randomized interventions.

The paper's architecture has five modules:
1. **Configuration Layer** — researcher-facing config defining the experiment (`experiment_design`, `sockpuppet_config`, `intervention`, `data_collection` namespaces).
2. **Sockpuppet Initialization & Persona Construction** — cold-start behavior (follow/engage until stopping criteria met, using a *restricted* action set) + a persistent `persona_prompt` (profile summary + behavioral rules) that governs an agent's decisions for the whole experiment.
3. **Agent Runtime** — the per-activation decision cycle: (1) Observation of platform state, (2) Prompt Construction (persona + platform state + experiment context + behavioral rules), (3) Decision (LLM call → structured `{action, target_object, system_response, execution_status}`), (4) Execution, (5) Logging. Activation timing is sampled from a configurable distribution (e.g. truncated power-law), not a fixed schedule. The *same* five-stage cycle runs during cold-start, pre-treatment, and post-treatment — only the allowed action set and experiment phase differ.
4. **Experiment Orchestrator** — global experiment state: account provisioning, per-agent activation scheduling, treatment assignment/randomization, phase transitions (init/pre-treatment → treatment → post-treatment), failure recovery, reproducibility logging.
5. **Data Collection & Storage** — immutable JSONL records: platform observations (for_you_feed, home_timeline, engagement_log, intervention_history) and full runtime logs (prompt, model output, action, execution result).

**Case study to reproduce**: the "Mercury Project" muting experiment. Sockpuppets are seeded from real Mercury participants' pre-treatment behavior (persona = summarized engagement/following patterns), split into control/treatment arms, and after a pre-treatment observation period, treatment agents mute a random 70% of a list of "untrustworthy" accounts they follow. Both arms continue being observed through a post-treatment period. The goal is to causally measure the effect of muting on subsequent exposure/engagement.

**Standing decisions** (already made with the user, don't re-litigate):
- Build order: **bugfixes → config → observation/action split → multi-account → LLM Agent Runtime → orchestrator** (roughly mirrors the paper's own module dependency order).
- Agent Runtime will use **LangChain** (user's explicit choice over a raw Anthropic-API-only design).
- GUI is **deprioritized** — paper only calls for a config file + a "Monitor & Control" component, not a UI. Revisit only after the orchestrator exists.
- Account provisioning / cookie automation is real ToS/detection risk — sequence it deliberately with its own risk review, and the user should confirm IRB/ethics approval covers automated multi-account behavior before scaling past 1 account. This is a process question for the user, not something to resolve in code.
- Multi-account credential storage was resolved as: **one gitignored `accounts.yaml`** with a list of account entries (credentials + optional per-account overrides), not per-account `.env` files or suffixed env vars. See Phase 3 below.
- Platform action rate limits (from live testing): **follow — 15/15min, 400/day**. Likes/mutes: no rate-limit issues detected so far. These constrain `initialization_params.min_follows` and any future activation-scheduling validation (Phase 4/5) — a configured `min_follows` must be reachable within `max_initialization_days` given the follow rate limit.

### Phase 4 — Agent Runtime (LLM decision loop) ✅ (live-verified; committing now — see repo for the actual commit hash)

Implements the paper's five-stage cycle using **LangChain** (`langchain-ollama` against a local Ollama server — the user's preference over a paid API; swap the model/provider in [src/runtime/decision.py](src/runtime/decision.py)): Observation → Prompt Construction → Decision → Execution → Logging. `TwitterScraper.run_agent_runtime()` ([src/scraper/twitter.py](src/scraper/twitter.py)) runs this loop forever, replacing the old scripted single-target observation loop for any account with `sockpuppet_config.persona_prompt` configured (`Account.agent_runtime_enabled`) — cold-start (4a) still runs first either way.

- **4a. Cold-start initialization mode ✅.** Restricted-action loop (follow/like/repost only, no mute/unmute) that runs before observation begins when `sockpuppet_config.initialization_params` is configured. Loops until `min_follows`/`min_engagements` are met or `max_initialization_days` elapses; progress persists in `agent_state` so a restart resumes rather than restarting, and a completed run never re-triggers. Follows are sampled (shuffled) from the configured `account_lists` and self-throttled to stay under the live 15/15min rate limit ahead of a 429. `main.py`'s `validate_cold_start()` rejects a `min_follows` that isn't reachable within `max_initialization_days` given the 400/day limit, at startup. Still a separate scripted loop, *not* routed through the new decision cycle (see the note near the end of this section).
- **4b. `AgentState` schema expansion** ([src/storage/agent_state.py](src/storage/agent_state.py)) — partial by design. `interaction_history`/`initialization_progress` landed with 4a; `record_interaction()` also accepts `execution_status`/`system_response`; `recent_interactions()` and `has_acted_on()` landed during live testing (see below). `persona_prompt`/`account_metadata`/`internal_memory` remain unbuilt — the persona text lives in a config-referenced file (`Account.get_persona_prompt_text()`) rather than in `agent_state`, and nothing needs per-agent `account_metadata`/`internal_memory` yet. Revisit if/when that changes.
- **4c. `execute_action()` structured return ✅** ([src/scraper/twitter.py](src/scraper/twitter.py)). Returns `{"execution_status": "success"|"failure"|"skipped", "system_response": {...}|None}` instead of a bare `bool` — `favorite_tweet`/`retweet`/`mute_user`/`follow_user` all return a small result dict (`success`/`status_code`/`reason`) that `execute_action()` wraps. `follow_all()` and cold-start check `result["execution_status"]` instead of truthiness.
- **4d. `No Action` ✅.** `execute_action("no_action")` short-circuits before the network with `{"execution_status": "skipped", "system_response": None}`. The `Decision` schema ([src/runtime/schema.py](src/runtime/schema.py)) includes it as a Literal option.
- **4e. Prompt construction ✅ (per-post as of the 2026-08-18 redesign below)** ([src/runtime/prompt.py](src/runtime/prompt.py)) — `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)` assembles `Prompt = Persona Prompt + Platform State + Experiment Context + Behavioral Rules` for ONE observed post at a time (+ a recent-actions section added during live testing, see below) as labeled sections. `experiment_context` (`TwitterScraper._build_experiment_context()`) provides `experiment_id`/`phase`/`treatment_arm`/`intervention_status`/`current_time` — the first three sourced from `experiment_design.experiment_name` + `sockpuppet_config.{phase,treatment_arm}`, explicit stand-ins for what the Experiment Orchestrator (Phase 5) will assign per-agent once it exists. `runtime_constraints` from the paper's schema isn't a separate field; it's folded into the `allowed_actions` list passed as behavioral rules. **Safety validation** (`_validate_decision()`) rejects a decision — downgrading to a logged `no_action` rather than calling `execute_action()` — if: the action isn't in `allowed_actions` for the current phase; the tweet's own data is missing the id `_resolve_target()` needs for that action (a data-quality problem, not a hallucination — see the per-post redesign below, there's no LLM-supplied id left to hallucinate); or the exact `(action, target)` pair already succeeded before (added during live testing, see below).
- **4f. Config schema widening** — landed: `sockpuppet_config.persona_prompt` (file path, resolved like `account_lists`), `sockpuppet_config.phase`/`treatment_arm` (Phase 5 stand-ins), `sockpuppet_config.activation_schedule.{distribution,min_interval,max_interval}` (parsed via new `src/utils/duration.py`; `truncated_powerlaw` approximated as log-uniform sampling, no shape parameter is given in the paper's schema to do better), `data_collection.logging` (`full`/`minimal`), `experiment_design.experiment_name`. The observed `platform_state` is persisted separately via the existing observation `FileManager`, matching the paper's treatment of platform observations and runtime logs as two distinct data streams.

#### Phase 4 live end-to-end testing (2026-08-18) — 3 real findings, fixed

Full `docker compose up` run with two real accounts in `accounts.yaml`: `primary` (no `sockpuppet_config.persona_prompt` — runs the old scripted single-target loop, unaffected by any of this) and `secondary` (persona = `personas/bradshaw_persona.txt`, a real gitignored persona the user wrote — see the orientation section below). Confirms the core milestone: **the full Observe → Prompt Construction → Decision → Execution → Logging cycle works end-to-end against the live X API** — real `like` actions landed successfully (`200 OK`, confirmed against the real account).

Also confirmed and closed out:
- **Activation-interval sampling is statistically sound.** An early observation (2 samples landing near the top of the configured range) looked suspicious; a longer run produced 6 samples (32s–111s) spread across nearly the full configured `[30s, 120s]` window, confirming `_sample_activation_interval()`'s `random.uniform`/log-uniform sampling works correctly — the earlier concern was just small-sample noise.
- **Activation spacing reminder**: the paper wants realistic **minutes-to-hours** spacing (`min_interval: 15m, max_interval: 6h` in its own worked example) to approximate real usage. The short `30s`–`2m` values used for testing are explicitly test-only — widen `secondary`'s `activation_schedule` before treating a run as a real experiment session.
- **`recent_interactions` fix landed**: `AgentState.recent_interactions(limit, exclude_actions)` + a new `=== YOUR RECENT ACTIONS (avoid repeating these) ===` prompt section so the model can see what it already did. **Necessary but not sufficient on its own** — see finding 1 below.

**Three findings from direct inspection of a real `runtime_log.jsonl`** (not fixture tests — this is what live testing surfaced that no amount of mocking would have caught):

1. **Repeats persisted even after the `recent_interactions` fix.** Checked the actual constructed prompt for a repeat decision: it correctly listed the target as already-liked, and the model liked it again anyway. A soft "please don't repeat yourself" instruction is not reliably honored by a 7B local model under simultaneous structured-output constraints. **Fixed with a hard rule, not a better hint**: `AgentState.has_acted_on(action, target)` + a third rejection branch in `_validate_decision()` — an exact repeat of a previously *successful* `(action, target)` pair is now always downgraded to `no_action`. A different action on the same target, or the same action on a new target, is still allowed.
2. **`follow` never triggered — a real bug, not a model failure.** The test persona's follow condition was "*fighting-game account with 1000+ followers*." `_format_tweet()` never rendered follower count at all, even though `build_tweet_object()` already collects `author.followers` — the model had no way to ever evaluate that condition. **Fixed**: `author_followers` added to the rendered tweet line in `_format_tweet()`.
3. **`mute` never triggered despite genuine matching content appearing.** Scanned all 15 real observed feeds in the log for political/Trump content (the persona's explicit "almost always mute" trigger) — cycle 1 really did contain a Trump-related tweet, and the model liked an unrelated tweet instead of muting it. This is a **genuine reasoning limitation** of a 7B model checking multiple persona rules against many candidates in one pass, not a data/code bug like #2. **Mitigated, not guaranteed-fixed**: added a rules line telling the model to explicitly check every specific "always"/"almost always" trigger condition before defaulting to its most common action. Whoever picks this up should re-test and see how much this actually moves the needle — it may need a stronger intervention (e.g. a two-pass decision, or scoping the platform_state down per cycle) if it doesn't.

All three fixes verified via fixture tests (mocked, no live calls — `has_acted_on` behavior, `_format_tweet` follower rendering, `_validate_decision`'s new rejection branch). **Not yet re-verified live** at the time these three findings were written — re-running `secondary` and checking whether repeats/follow/mute now behave correctly was the natural immediate next step, and turned out to surface a deeper root cause (below).

#### Follow-up (2026-08-18, same day): root cause of finding 3, and why follow rarely fired either

A user-reported log (all 15 decisions in `run_20260818-103350_runtime_log.jsonl` were `like`, never mute/follow/retweet) prompted a direct, reproducible diagnosis: isolated `DecisionEngine.decide()` calls (real Ollama, `qwen2.5:7b`, no live X API) against small engineered feeds, run 10-12x each to see the actual decision distribution rather than judging from one-off samples.

- **Confirmed not a code/validation bug**: the saved `model_output` field in the real runtime logs shows the LLM itself emitting `action: "like"` in all 29 decisions logged that day (the `no_action` entries visible in `selected_action` are `_validate_decision` correctly downgrading repeat-`like`s via `has_acted_on` — the raw model output was still always `like`).
- **Root cause 1 — competing salience crowds out conditional triggers.** A feed with only a mute-worthy tweet (no fighting-game content) *did* get muted ~30% of the time. The same mute-worthy tweet placed alongside a fighting-game tweet got muted 0/10 times — the model reliably defaults to its "primary" persona behavior (like/retweet) whenever anything resembling it is present, rather than checking conditional rules first. This matches the finding-3 hypothesis above (7B model, multiple rules, one pass) but is worse than it looked: it's not "sometimes misses it," it's "never checks it once a like-candidate exists in the same context."
- **Root cause 2 — id-type confusion for follow/mute, once the model does try to act on the author.** Even after root cause 1 was fixed (below) and mute/follow decisions started coming through, the model would sometimes hand back the tweet's `tweet_id` as `target_object` for a `mute`/`follow` action instead of the author's `user_id` — because `_format_tweet()`'s old `[id: ..., author_id: ..., ...]` labeling made "id" ambiguous about which value maps to which field. `_validate_decision()`'s hallucinated-id check would then correctly reject it (the tweet_id genuinely isn't a valid user_id) and silently downgrade a well-reasoned mute/follow to `no_action` — so this bug would have kept suppressing mute/follow even after root cause 1 was addressed.
- **Fix, verified empirically (not just fixture tests) against real Ollama output**:
  - [src/runtime/schema.py](src/runtime/schema.py): `Decision` gained a `trigger_check: str` field placed *before* `action` — pydantic/tool-calling field order is generation order for structured output, so forcing the model to articulate which persona trigger (if any) matches which observed item, before it commits to `action`, changed behavior directly (this is a generation-order effect, not just better wording).
  - [src/runtime/prompt.py](src/runtime/prompt.py): `_format_tweet()` relabeled `id:`/`author_id:` to unambiguous `tweet_id:`/`author_user_id:`; `RUNTIME_BEHAVIORAL_RULES` updated to match and to spell out that follow/mute target the author's `author_user_id`, never the `tweet_id`.

#### Fourth follow-up, same day: per-post redesign — one LLM call per post, not one per batch

Even with `qwen2.5:14b`, a live run still came back all `like`/`no_action` (`run_20260818-142556_runtime_log.jsonl`). Per the user's own diagnosis: the underlying problem is prompt size/complexity, not just model capacity — one prompt asking the model to weigh ~28 competing candidates at once is a hard reasoning task regardless of model size. The user's proposed fix: send one prompt per individual observed post instead of one prompt for the whole batch, accepting that this makes each activation much slower (N tweets = N LLM calls) since realistic `activation_schedule` intervals (minutes to hours) comfortably absorb it.

**Checked against the paper first** (`SockPuppet (1).docx`, extracted from the user's Downloads folder via the docx skill, since it wasn't otherwise available in this conversation). This is well-supported, not just permitted: the paper's own worked Mercury Project example describes the persona-driven engagement decision literally as **"for each X item in the feed, decide whether or not to engage"** — a per-item process. Section 3.3's `Decision` interface (`action`/`target_object`/`system_response`/`execution_status`) describes the *persisted record's* fields, not a mandate that one LLM call must span an entire `platform_state` — and this codebase's own `schema.py` already established that precedent (`system_response`/`execution_status` are filled in by the runtime after execution, never generated by the model).

**Implementation** (planned via `EnterPlanMode`, one Plan-agent review pass, then executed):
- [src/runtime/schema.py](src/runtime/schema.py): `Decision` drops `target_object` entirely. Since each prompt now concerns exactly one known tweet, the runtime already knows that tweet's `tweet_id` and its author's `user_id` deterministically — there's no id left for the model to hallucinate or confuse. This *fully* closes the tweet_id-vs-author_user_id confusion bug from the second follow-up above (previously only mitigated via clearer labeling, never eliminated). Kept `trigger_check` (still forces the model to reason before committing to `action`, field order still load-bearing), reworded for a single-post framing.
- [src/runtime/prompt.py](src/runtime/prompt.py): `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)` replaces the old whole-`platform_state` version. `format_platform_state()` removed (dead code once nothing calls it); `_format_tweet()` reused as-is for the single "OBSERVED POST" section. `RUNTIME_BEHAVIORAL_RULES` rewritten: dropped all now-meaningless `target_object`-format rules; reframed "prefer a different item from the feed" (assumed other items to fall back to) into "choose a different action on this post, or no_action"; reframed "scan the feed for a matching trigger" into "check THIS post specifically."
- [src/scraper/twitter.py](src/scraper/twitter.py): new `_resolve_target(action, tweet)` derives the target deterministically (tweet_id for like/retweet, author's user_id for follow/mute, None for no_action) — can still legitimately return `None` if the tweet's own data is missing that id (a data-quality issue, not hallucination, gets a distinct log message). `_validate_decision(decision, tweet, allowed_actions)` (was `(decision, platform_state, allowed_actions)`) drops the hallucinated-id check entirely (structurally impossible now) and calls `_resolve_target()` instead. `_log_runtime_cycle()` gains `observed_tweet_id`/`target_name` params (see Runtime logging note above). `run_agent_runtime()`'s outer loop is unchanged (still one `observe()` snapshot per activation, still samples the next interval only after all posts from this activation are processed) but the single decide/validate/execute/log block is now a nested `for target_name, tweets in platform_state.items(): for tweet in tweets:` loop, with `experiment_context`/`recent_interactions` recomputed on every inner iteration (so `current_time` doesn't go stale across a long inner loop, and an action taken on post #3 is visible to post #10's prompt in the same activation). An all-empty activation (zero tweets across every target) still writes one lightweight `no_action` runtime_log row, preserving the "one log row exists per activation" audit trail rather than silently going quiet.
- Cold-start (`run_cold_start()`) is untouched — confirmed it never touches `construct_prompt`/`DecisionEngine`/`Decision`/`_validate_decision` at all, so this redesign doesn't affect it.

**Verified** by feeding the real, already-captured 28-tweet `for_you_feed` batch from `data/2026-08-18/twitter/secondary/run_20260818-142556.jsonl` through the new per-post pipeline against the real local Ollama server (`qwen2.5:14b`), one tweet at a time: **no_action: 15, like: 6, mute: 4, follow: 3** — full diversity across every action, zero missing/malformed target ids (guaranteed now, not just observed, since ids are code-derived rather than model-supplied). This is a dramatic improvement over every prior batch-based attempt (7b: 12/12 `like`; 14b batch: still mostly `like`/`no_action` on a live run). **Live-verified the same day** — the user ran it live and confirmed a healthy real spread (`like`/`mute`/`follow`/`no_action` all appearing across one run's `runtime_log.jsonl`).

#### Fifth follow-up, same day: distinguishing WHY a row is `no_action`

Once live results looked good, the user wanted `runtime_log.jsonl` to distinguish three different reasons a row can end up `selected_action: "no_action"` -- previously indistinguishable from the log alone:
1. the model genuinely looked at this post and decided no_action was the right call,
2. it was downgraded because it exactly repeated an `(action, target)` that already succeeded before (the `has_acted_on` hard rule), or
3. it was downgraded because the decision itself couldn't be honored (action not allowed this phase, or this post's own data was missing the id the chosen action needed).

`_validate_decision()` ([src/scraper/twitter.py](src/scraper/twitter.py)) now returns a third value, `no_action_reason`, alongside `(action, target)`: `"chose"` / `"repeat"` / `"failed"` respectively, `None` for any non-`no_action` decision. `_log_runtime_cycle()` gained a matching `no_action_reason` param, written into every runtime_log row (always present, `None` when not applicable, matching this file's existing convention of consistent JSONL keys). The all-empty-activation row (nothing observed at all, added in the per-post redesign above) gets a fourth value, `"nothing_observed"`, since no LLM call happened at all in that case -- not the same as the model looking at a post and choosing not to act.

Verified against real captured feed data: replayed the same 28-tweet batch, confirmed genuine model no_actions tag `"chose"`, a forced-repeat of an already-successful decision tags `"repeat"`, and a forced disallowed-phase decision tags `"failed"`.

#### Eighth follow-up (2026-08-26): retweet's silent no-op — a real bug, not a repeat of the id-confusion history above

Live testing (persona changed to prefer `retweet` for one run, specifically to exercise this path) surfaced a new failure mode: `execute_action("retweet", ...)` returned `"execution_status": "success"`, `"system_response": {"status_code": 200, "reason": "OK"}`, but the repost never appeared on the post or the account's Reposts tab.

**Root cause**: `favorite_tweet()`/`retweet()` ([src/scraper/twitter.py](src/scraper/twitter.py)) determined success from `r.status_code == 200` alone and discarded the response body entirely (`system_response` only ever stored `status_code`/`reason`). X's GraphQL mutations routinely return **HTTP 200 with an `errors` array and null data** when the mutation itself fails — a 200 status is not proof the action happened, and the discarded body meant there was no way to see *why* from the logs.

**Fix**: both methods now route through a shared `_post_graphql_mutation()` helper that parses the JSON body and treats a non-empty `errors` array as failure, surfacing the real error message as `reason`. Also added `"dark_request": False` to `CreateRetweet`'s variables (part of X's real mutation payload for this endpoint, plausibly why it silently failed while `FavoriteTweet`, which doesn't need it, worked).

**Re-run with the fix in place surfaced the actual reasons**, confirming this wasn't a code bug but genuine anti-automation behavior from X:
```
retweet → 404 Not Found                                                              (x4)
retweet → 200 OK, but "Authorization: This request looks like it might be automated" (x2)
like    → 200 OK, but "Authorization: Actor (uid: ...)..."                            (x1, recovered afterward)
```
The mix of 404s and an explicit "looks like it might be automated" message on the *same* endpoint (rather than a uniform failure mode, which a stale query hash would produce) points to X's backend giving inconsistent/obscured responses to a request it's flagged as automated — retweet appears to be far more heavily monitored than like/follow/mute. `like`/`follow`/`mute` kept succeeding throughout the same run, so this is a per-action/per-moment detection heuristic, not an account-wide lockout. **A re-run the same day came back clean** (no automation rejections), consistent with this being an intermittent, behavior-triggered detection rather than a permanent block. Treat as a documented platform-behavior finding, not something to engineer around.

**Also fixed the same day**: `execute_action()` now logs a clear `[action] {action} on {target} FAILED: {reason} (status_code=...)` line whenever *any* action fails (like/retweet/follow/mute), for every caller that goes through it (the runtime decision loop, cold-start follows/engagements, `follow_all()`) — previously a failure's reason was only ever visible by digging into `runtime_log.jsonl`'s `system_response`, easy to miss live.

Both fixes syntax-checked; the GraphQL-error-body fix was live-verified via the re-run above (real error messages surfaced correctly). **Known residual gap, not new**: if a mutation returns `200` with an unparseable JSON body, `errors` stays `None` and it's still reported as success — same laxness the old status-only check had for that specific edge case, not fully closed by this fix.

### Empty-batch exponential backoff (2026-08-18)

The `primary` account (old scripted `for_you_feed` loop, no persona) was reported to be collecting fewer new posts over time — matches the pre-existing "For You tab pagination is not indefinite" known issue above: `_scrape_timeline()` was hammering the API with only the flat `scroll_delay` between fetches even when an entire page came back as 100% already-seen duplicates.

Added exponential backoff scoped to exactly that condition: in `_scrape_timeline()` ([src/scraper/twitter.py](src/scraper/twitter.py)), a run of consecutive batches with zero new tweets (after the existing `seenTweetIds` dedup) now waits `empty_batch_backoff_base × 2^n` seconds, capped at `empty_batch_backoff_max`, on top of `scroll_delay` — reset to zero the moment a batch has any new tweet. Only applies to `for_you_feed`/`search` (the two `track_seen_ids=True` targets, where "new vs. duplicate" is actually computed); `home_timeline` doesn't dedupe at all today and wasn't touched. Three new config keys (`empty_batch_backoff_base` default `5`, `empty_batch_backoff_max` default `300`, `empty_batch_backoff_jitter` default `0.2`), per-account overridable like the rest — added to `config.yaml`, `accounts.yaml.example`'s exhaustive reference block, and README's config table. **Live-verified (2026-08-26)**: `primary`'s empty-batch stretches now visibly back off instead of hammering at a flat 2s.

**Follow-up, same day**: per the user's request, the backoff is now jittered rather than a clean exact doubling -- each wait is `(base × 2^n)` randomized by `± empty_batch_backoff_jitter` (default ±20%, still capped at `empty_batch_backoff_max`), so consecutive waits don't form a mechanically perfect 1x/2x/4x/8x/... sequence, which would itself be a detectable non-human pattern. Verified the formula's distribution in isolation (samples cluster around the doubled value with the expected spread at several `n`); **live-verified (2026-08-26)** alongside the base backoff confirmation above.

Also completed this session, smaller items: `accounts.yaml.example` now has an exhaustive `reference_example` block documenting every possible per-account field (standing instruction from the user — keep this in sync whenever a new config field is added, don't treat it as a separate follow-up); `.gitignore` now excludes everything under `personas/` except `example_persona.txt.example`, so the user's real persona file(s) never get committed.

## 3. Remaining roadmap

**Phase 5 — Experiment Orchestrator** *(next)*
- Global experiment state (`experiment_id`, `current_phase`, `scheduler`, `activation_queue`, `treatment_assignment`, `intervention_schedule`, `experiment_status`), shared across all agents (unlike per-agent runtime state).
- Seven responsibilities per the paper: (1) account provisioning (`agent_id`/`persona_prompt`/`experiment_id`/`initialization_params` per account), (2) runtime scheduling (real per-agent randomized activation intervals — NOT an OS cron job; supersedes Phase 3's one-thread-per-account stand-in; must also respect the 15/15min follow rate limit across concurrently-active agents), (3) treatment assignment/randomization, (4) intervention execution, (5) phase transitions (deterministic state machine: init/pre-treatment → treatment → post-treatment), (6) failure recovery (isolated per-agent, doesn't halt the experiment), (7) reproducibility logging (every scheduling decision, assignment, intervention, phase transition, failure, and termination event).
- This is what actually runs the Mercury muting case study end-to-end.

**Phase 6 — Data Collection & Storage expansion**
- Extend `FileManager`'s JSONL output to the paper's exact schemas (schema-widening, not a storage migration — JSONL stays the format):
  - **Observation schema**: `observation_id`, `timestamp_utc`, `experiment_id`, `agent_id`, `phase`, `treatment_arm`, (+ the platform-specific payload).
  - **Runtime log schema**: `log_id`/`observation_id`, `timestamp_utc`, `platform_observation`, `constructed_prompt`, `model_output`, `selected_action`, `target_object`, `execution_result`, `system_response`, `execution_status`.

**Ongoing / lower priority (not blocking anything):** structured logging (replace bare `print()`/`self._log()`), a test suite, run-archival (zip old runs), a status CLI (in place of the deprioritized GUI).

## 4. Orientation — key files

- `accounts.yaml` — gitignored, per-account credentials + optional per-account overrides of anything in `config.yaml`. `accounts.yaml.example` is the committed template.
- `src/config.py` — `Account` class (resolved per-account credentials + merged config); `Settings` singleton (`settings`) loads `config.yaml`/`.env` and exposes `load_accounts()`.
- `src/main.py` — entry point; validates every account's resolved config, then runs each account's scraper in its own thread.
- `src/scraper/base.py` — `BaseScraper` ABC, takes a single `Account` (`self.account`), abstract `run`/`fetch_home`/`fetch_following`.
- `src/scraper/twitter.py` — GraphQL timeline fetchers, `parse_timeline()`, `execute_action()`, all four platform actions, cold-start (`run_cold_start()`), and the Agent Runtime cycle (`observe()`/`run_agent_runtime()`/`_resolve_target()`/`_validate_decision()`/`_log_runtime_cycle()`), all keyed off `self.account`. `run_agent_runtime()` loops per-post within each activation (2026-08-18 redesign) — see Phase 4 below before assuming one decision = one activation. **Naming key (2026-08-19), read this before touching timeline-fetching code**: GraphQL operation `HomeTimeline` = X's algorithmic default feed = our `home` target (`fetch_home()`/raw `fetch_home_timeline()`); GraphQL operation `HomeLatestTimeline` = X's reverse-chronological feed = our `following` target (`fetch_following()`/raw `fetch_home_latest_timeline()`). - `src/scraper/x_client.py` — `x-client-transaction-id` generator (X's anti-automation request signing). No per-account state, safe to call from multiple threads.
- `src/runtime/schema.py` — `Decision` pydantic model (the LLM's structured output for ONE observed post: `trigger_check`/`action` only — no `target_object`, since the per-post redesign (2026-08-18) derives that deterministically in `TwitterScraper._resolve_target()` instead of trusting the model to supply it).
- `src/runtime/prompt.py` — `construct_prompt(persona_prompt, tweet, target_name, experiment_context, allowed_actions, recent_interactions)`: assembles persona + ONE observed post + experiment context + behavioral rules into the text sent to the LLM (per-post as of the 2026-08-18 redesign — was whole-`platform_state` before that).
- `src/runtime/decision.py` — `DecisionEngine`: wraps a LangChain `ChatOllama` call (local Ollama server, `DEFAULT_MODEL = "qwen2.5:14b"`) with structured output. Swap the model/provider here without touching prompt/schema.
- `src/utils/duration.py` — parses shorthand durations (`"15m"`, `"6h"`, `"7d"`) used by `activation_schedule`.
- `personas/example_persona.txt.example` — template for `sockpuppet_config.persona_prompt` files (profile summary + behavioral tendencies). Not real Mercury data. `personas/bradshaw_persona.txt` (gitignored, real content) is the user's actual test persona — currently wired to the `secondary` account in the user's local (gitignored) `accounts.yaml`, with `sockpuppet_config.activation_schedule` set to short test intervals (30s–2m, not the realistic 15m–6h). `primary` in that same file has no persona configured and still runs the old scripted loop.
- `src/storage/file_manager.py` — JSONL writer, namespaced by account name; timezone is a per-instance param; `stream` param disambiguates multiple concurrent writers per account (observations vs. runtime log).
- `src/storage/agent_state.py` — per-account state persistence: `following_list`/`muted_accounts`/`interaction_history`/`initialization_progress` (see Phase 4b for the fields still missing).
- `README.md` — user-facing setup/config docs, kept in sync with `config.yaml`/`accounts.yaml`'s actual schema each phase.

## 5. Working agreements worth knowing

- Don't run `docker compose up` / hit the live X API autonomously — it performs real actions (follows, timeline fetches) against the user's real account(s) with live credentials. Verify logic locally (unit-style scratch scripts, synthetic fixtures) and ask the user to run live verification themselves.
- Only commit/push when explicitly asked, and only the files actually intended (check `git status`/`git diff` before staging — this repo has real secrets in gitignored `.env`/`accounts.yaml` that must never get staged).
- Corrections to this roadmap are welcome and expected — several past checklist items have turned out to be stale (e.g. an old note about Search being blocked by a missing header that was already resolved before Phase 2 started). Treat this file as living documentation, not a fixed contract.
